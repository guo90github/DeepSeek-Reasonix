# 事故报告：聊天室循环 09:04–14:10 停摆（2026-09-27）

**结论（三句话）**：
1. 房间的 6 条唤醒**都送达并入了队**（HTTP 202 + 入队回执），但**一条都没被消费**——队列处在"保持暂停"那一档，等的是人点「继续执行」。
2. 与此同时，这个会话的上下文涨到 **~1.07M–1.15M tokens > 模型上限 1,048,576**，**压力触发的自动压缩自己被 400 拒了**（压缩请求本身超窗）⇒ 即使放行，回合也起不来。
3. 两个故障**叠在一起**，而两边看到的信号都是"没事"（房间看到 idle、宿主看到 202 已送达）——所以 5 小时没人发现。

本报告只**读取**了 Reasonix 自身的状态文件（会话目录、日志、清单），**没有任何写入**。

## 二、根因链

### A. 队列被"保持暂停"，唤醒只排队不放行（先发生）
- 唤醒走的是入队路径，**入队成功 ≠ 会跑**：入队只回 202，真正跑起来还要队列**没有暂停**且运行时就绪。
- 09:04–09:25 的五条入队都成功，回执却一直**没有 disposition**，直到 14:10 被**删除** —— 期间没有被 dispatch 过。
- 暂停是**人在界面上按的**（或恢复后默认保持）：`InboxRecoveryBanner` 的两颗钮就是 `SetInboxPaused(false/true)`。恢复（重启后 `recovered`）会**停在暂停态等你确认**，这是设计上的安全阀。
- **未见直接记录**：状态文件里没有暂停的时刻流水（清单只有当下的 `paused` 布尔），所以"何时、被谁置为暂停"只有界面截图与代码路径两条间接证据——本报告不把它写成事实。

### B. 会话上下文超过模型窗口，自动压缩自己也被 400 拒（叠加，致命）
- 两条 WARN 是硬证据（13:52:44、14:01:43）：**压缩请求本身超窗**被服务端 400 拒绝。
- 一旦如此，**任何新回合都起不来**：回合开跑前要先压缩，压缩失败 ⇒ 拿不到可发送的上下文 ⇒ 我在 09:25 之后就再也跑不动（这解释了 4.5 小时零产出，且与 A 是两回事：即使放行也没用）。
- 会话这么大是因为这条聊天室循环**在一个会话里连轴跑**：整夜的批次、每笔交付的长文本、以及工具输出全部留在同一个上下文里。

### C. 双方都看不见故障（放大器）
- 房间侧：`wake` 得到 202 ⇒ 记录成"已送达"，此后**没有回执通道**（`docs/COLLAB-SURFACE.md` §7 已经写明这条路是"按 seq 问"）；对侧只能看到 `idle`，于是互相等。
- 我这边：故障只落在**日志的 WARN** 里，没有任何 UI/协议面把"这条行排了 5 小时没跑"说出来。`InboxSnapshot` 有 `paused`，但**房间问的那条路（`/inbox/room-line`）没答它**。

## 三、解决方案

### 1) 代码（按优先级，每条附可验收判据）

**P0 — 压缩不许把回合锁死**（`internal/agent` 压缩路径）
- 当摘要输入本身超窗（400/上下文过长）时，**逐级降级**而不是放弃：① 按 span 分块摘要（多请求、每块在窗内）；② 仍不行就**硬降级**：丢弃最老的 span 直到请求落进窗口，并写入一条"因上下文超窗已裁剪"的可见说明。
- 判据：构造上下文 > 窗口的会话夹具 + provider 返回 400，断言**回合仍能起跑**，且历史里出现裁剪说明；再断言降级链每一级都有测试（块摘要在窗内、硬降级后请求 token 数 < 窗口）。
- 反例必须红：把降级关掉 ⇒ 用例当场红（今天这个 5 小时死锁就是它的实际后果）。

**P1 — "入队 ≠ 会跑"要有看门信号**
- `InboxSnapshot` 已有 `paused`；**让 `/inbox/room-line` 也答它**（`paused` + `queuedForMs` 已有 + 新增"为什么还没跑"的闸名），这样对侧/人问一句就知道是"被握着"而不是"没送达"。
- 阈值告警：排队超过 N 分钟仍未 dispatch ⇒ 记一条明确事件（并在桌面可见），文案区分两档：**队列暂停** vs **回合起不来（压缩/模型失败）**。
- 判据：两条路（暂停 / 压缩失败）各一条用例，断言 `room-line` 答出可区分的 `gate`/`reason`；变异红：把 `paused` 从回答里去掉 ⇒ 当场红。

**P2 — 大上下文会话要有"该换会话了"的显式提示**
- 当会话 token 数逼近窗口（例如 > 窗口 60%）就提示；压缩失败已发生时给出**可执行动作**（新开会话 / 清上下文），而不是只在日志留 WARN。

### 2) 运维动作（立刻可用）
1. 桌面那颗「**继续执行**」——放行被握住的队列；
2. 出现 `compaction failed … maximum context length` ⇒ **换新会话**（本次就是 13:56 起的新会话 `20260927-054743…` 在继续服务）；
3. 长循环按批**收口**，不要在同一会话里连轴跑几小时。

### 3) 工作流纪律（两边都适用，写进各自的规矩）
- **每批结束就 `@done` 收口**，或换会话再开——今天这批 B#1091/B#1111 之间就是这样卡住的；
- 房间侧：`wake` 拿到 202 后，**要能追问**（`/api/wake-receipt` / `/inbox/room-line`），并在自己那侧把"排了多久没跑"显示出来；
- 我这边：收到 wake 后**先确认能跑起来**（回合已启动）再算接手，起不来就当场回报"起不来 + 原因"。

## 四、怎么复核（证明修好了）

1. **压缩降级**：`go test ./internal/agent/ -run 'Compact|Pressure|Context'` 全绿，且新增的"超窗夹具 + 400"用例能跑通；把降级关掉时该用例红。
2. **看门信号**：`go test ./internal/serve/ ./desktop/ -run 'RoomLine|Inbox'` 绿；用真 http 处理函数断言 `paused`/`gate` 出现在回答里。
3. **端到端复现这次事故**：造一个队列暂停的会话 + 入队若干条 → 问 `room-line` ⇒ 必须答出"暂停中、已排 N 秒"，而不是光秃的 `found:false`。

## 五、未验证与边界（照实）

- **暂停被谁、在何时置上**：状态文件里没有这个流水，只有界面截图与代码路径；要落成事实得先给 `paused` 加一条时间戳/事件（这也是 P1 的一部分）。
- 09:25–13:52 之间**是否真的有过模型请求尝试**：日志只记 serve 层请求与 WARN，agent 的每次 provider 调用不逐条落日志；因此"这段时间没有任何尝试"是从"没有输出、没有回执、没有 WARN"推出来的，不是直接观测。
- 上述日志里的行号来自本机 `service.log`（跨多次重启追加），换机器需按同一模式重新取证。
- 本报告只读状态文件；**没有修改任何会话数据**。
