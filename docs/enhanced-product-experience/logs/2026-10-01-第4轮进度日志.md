## 已完成

- ✅ **C 类先按子类拆开**（这是本轮第一个结论）：语料 91 次不是同一件事 ——
  - **60 次**（32+28）=「一条命令里先改后验」被 shell-contract 拦下（`ShellContractPreflightMessage("mixed")` / `execute_one.go:352`），性质是**调用姿势**；
  - **31 次**（14+12+5）= 批次内前序写失败/被拦后，后续**验证被跳过**（`mutationBarrierCause.message`），性质是**设计**（`batchCallStaticallySkippable` 明确写着 "a check after a failed change proves nothing"）。
- ✅ **「自动补跑被跳过的验证」判定：不落地**（假设 A-17）。探针实测 `shellsafe.ClassifyBash`：`go test ./...`、`gofmt -l`、`npx tsc --noEmit`、`go run ./tools/repolint` **都无静态只读保证**；有保证的只有 `go vet` / `git status` / `git diff`，而这一类**本来就会跑**（`batchCallStaticallySkippable` 对已证明只读的诊断返回 false）。⇒ 原计划的前提（"验证命令静态可判只读"）几乎不成立：要补跑就得放宽保守规则，换来的却是「跑在没有修好的状态上」。收益≈0、风险为正。探针为临时文件，已删除（`git status` 无残留）。
- ✅ **A-3「拦截即给可直接采用的下一步」落地**（假设 A-18），目标是上面 60 次那一类：
  - `internal/evidence/evidence.go`：`ShellContractPreflightMessage(reason, command)` 附带 `ShellContractSplitHint(command)` —— 用 `shellparse.SplitTopLevel` 把模型**自己的**命令按顶层段拆开，渲染成「把它分成 N 次调用，按这个顺序：1) … 2) …」；
  - `internal/agent/execute_one.go`：三个 shell-contract 拦截点（含闭环版字面文案）都带上提案；
  - 边界：段数 > 4、渲染 > 1024 字节、单段、解析失败 ⇒ 不给提案。
- ✅ **验收闭环（本轮的验证要点）**：提案必须能通过拦下复合命令的**同一套守卫**，否则"重试"还是被拦 ——
  - `TestSplitHintProposalPassesTheSameContract`：把提案里每一段单独喂给四个守卫，全部放行；
  - `TestSplitHintStaysEmptyWhenThereIsNothingToSplit`：四种不该提案的情形确实不提案；
  - `TestShellContractRefusalCarriesTheSplitToTheModel`：面向模型的结果里确实带着 `1) go generate ./...` / `2) go test ./...`。
- ✅ **验证**：`go build ./...`=0；`gofmt -l internal/agent internal/evidence` 干净；**`go test ./internal/evidence/ ./internal/agent/ ./internal/boot/` 三包全绿**（`ok 0.1s` / `ok 69.3s` / `ok 154.7s`，本轮 agent 包未再出现前几轮的 flaky）。
