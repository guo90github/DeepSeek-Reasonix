## 三、目标语义与口径

1. **不阻塞**：一次循环里遇到会长时间运行的调用，宿主**不因它把整批/整轮拖住**——把该调用转成后台作业，批次立即收口。
2. **事后收取**：作业结果用既有 `bash_output` / `wait_job` 取回；完成时按既有作业通知路径告知。
3. **保序**（不可省的约束）：同批**后续调用不得提前执行**——否则"先写后台跑、后调用来读"会产生顺序错乱的观测。故后续调用要**延迟**（如实说明原因），由模型在收取作业后重发。
4. **单步 ≤1000ms 口径（假设 A-04）**：只计**宿主侧**——即"派发该调用 → 本轮收口"的时间，不含命令自身运行时长、不含模型推理与网络。仪器就是 §一 那支 effect test：把规则打开后，同样的批次里"下一次模型往返"的间隔必须远小于 `sleep 2`（目标 < 1000ms）。

## 四、设计（定稿，实作待做）

**决定必须发生在启动之前。** 前台 `bash` 一旦跑起来就无法热转后台：杀掉重启会重复副作用（写文件、装包、改仓库状态）。因此规则是"启动前判断"，而不是"跑到一半再搬走"。

规则（`executeBatch` 串行路径，`internal/agent/execute_batch.go:266-317`）：

1. 若当前调用是 `bash`，且该参数**未**显式带 `run_in_background`，且**本批在它之后还有未填的调用**，且**档位**判定为"该转"：
   → 就地把该调用参数补上 `run_in_background: true` 后再执行（`bash` 自身会启动作业并立刻返回 `Started background job …`，结果自解释）；
2. 同时把本批其余未执行的调用按"**延迟**"处理：给一条如实的结果——"前序调用已转后台作业 `<job id>`；先用 `bash_output` / `wait_job` 取回它，再重发本调用"（与既有依赖屏障的跳过文案同族，但原因不同，故用独立措辞）；
3. 交付策略（档位）：
   - **极速模式**：只要 `bash` 与本批后续调用同批，就转后台（最激进）；
   - **平衡（默认）**：只对宿主识别为"验证/构建"形状的命令（复用 `evidence.IsVerificationCommand`）转后台，其余保持前台；
   - **关**：一律不自动转（= 今天的行为）。
4. 与既有机制的关系：转后台**不是失败**，不触发依赖屏障；`complete_step` 的回执要求不变（验证类命令被转后台后，必须**先收取**再算数——这是模型侧的行为约束，写进提示词/结果文案）。

**档位与"拖拽按钮"**：档位就是上述**激进度**这一个旋钮；前端拖拽控件是它的界面形态（后续需求第十/第十七同属桌面交互批次）。宿主侧先落"旋钮 + 规则"，界面后接。

### 7.2 ⚠️ R-9 的真身：**收取后台作业不会为原命令留下验证回执**

写文案时查证发现的**功能缺口**（不是文案问题）：

- 前台验证 → `ReceiptFromToolCall("bash", args)` 记下命令文本 → `HasSuccessfulCommand(cmd)` 可匹配 ⇒ `complete_step` 通过；
- 后台作业（自动转或模型显式）→ 回执的 `command` 是**空的**（`bgjobs.go` 全文没有 command 映射，`wait_job`/`bash_output` 也不携带作业的原命令）⇒ 即便模型老老实实收取并拿到退出码 0，**也换不来一条该命令的验证回执**，`complete_step` 仍会认为"这条验证没跑过"。

因此当前文案只能解释现象，**不能真正闭环**。闭环的设计（下一轮实作）：

1. 转后台时（`promoteShellCallToBackground`）与显式后台时，都记下 `jobID → 原命令文本`（promotion 处有 `calls[i].Arguments`；job ID 从该调用的结果/执行元数据取，必要时给 `ShellExecution` 加一个显式 `JobID` 字段，避免解析文案）；
2. 模型收取（`bash_output`/`wait_job`）且作业终态为**成功**时，宿主按记下的原命令补一条 `Receipt`（`ToolName:"bash"`、`Command:原命令`、`Verification` 同前台），退出码取自作业的终态；
3. 补测：`后台跑 go test → 收取 → complete_step 引用它可通过`，以及"作业失败时不得记为成功验证"。

未见此改动前，**默认档保持 `off` 的理由又多一条**（见 7.3）。

### 7.3 ② 三档真机实测与默认档决策

同一支 effect test 家族（`internal/boot/loop_async_effect_test.go`），批次 `[bash(<命令>), read_file]`，机器与装配一致：

| 档位 | 命令 | 本轮实测"下一次模型往返"间隔 | 是否提升为作业 | 后续调用 |
|---|---|---|---|---|
| `off`（默认） | `sleep 2` | ~2138 ms（见第 5 轮基线 2137） | 否 | 正常执行 |
| `balanced` | `go vet ./...`（检查形状） | **11 ms** | 是 | 被延迟 |
| `balanced` | `sleep 2`（普通形状） | **2138 ms** | 否 | 正常执行 |
| `fast` | `sleep 2` | **18 ms** | 是 | 被延迟 |

读数与决定：

1. **`balanced` 并不解决需求里的那个场景**——需求举的例子是"一个 bash 脚本卡几分钟"，脚本属**普通形状**，balanced 依旧等满（2138 ms）。
2. **`fast` 也不宜做默认**：它按"同批有后续调用"一律提升，于是日常的 `[gofmt -w ., go test]` 这类**短命令成链**会被拆成"前者后台、后者延迟"，比今天的串行更糟（多一次收取与重发）。
3. 需求本身要的是**用户可控的档位**（"附带一个拖拽按钮……最高档为极速模式"）⇒ **默认档保持 `off`**，把三档连同上面这张实测表交给用户去选：要检查类提速选 balanced，要在长流程里继续干活选 fast。

> 这也与项目既有的"开关是唯一闸门、且默认不变行为"的口径一致。

### 7.4 ③ 前端控件排期（与第十/第十七 同批）

## 八、A-23 闭环落地（2026-10-01 第 8 轮）

### 8.1 现在的语义链

| 环节 | 行为 |
|---|---|
| 起动后台 | `bash` 的执行元数据带出 `JobID`（`tool.ShellExecution.JobID`，由 bash 后台分支写入）；宿主记下 `jobID → 原命令`（`shellJobCommands`，`internal/agent/shell_job_receipts.go`） |
| 起动**不算数**（新发现，见 8.2） | 起动那张回执被降级：`Success=false` 且**抹掉 `Command`**（`degradeBackgroundStartReceipt`）——既不再匹配"成功跑过"，也不再匹配"跑过但失败" |
| 收取 | `bash_output` / `wait` 现在**结构化**带出作业终态（`ExecuteDetailed` + `ExecutionDescriptor`），agent 在 `finalize` 里按 `jobID` 取回原命令 |
| 记功 | 终态 **completed** ⇒ 补一条 `bash` 回执（`Command=原命令`、`Success=true`），并在收取结果里写明"collected as receipt r_… for `<cmd>`；cite it to sign this off"；**failed / killed / 仍在跑** ⇒ 不产生成功回执（failed/killed 记一条失败回执，仍在跑什么都不记） |

### 8.2 顺带查出的两个真缺陷（都不是本次新引入，但都影响第九的可用性）

1. **起动一张回执就能冒充"跑过"**：此前 `bash(run_in_background)` 的回执是 `Success=true` + `Command=原命令`，于是 `HasSuccessfulCommand(cmd)` 在**作业还没跑完**时就为真——`complete_step` 会接受一条根本没结束的验证。这条洞在今天之前一直存在（只是以前没人把验证类命令放后台）。修法即 8.1 的"降级起动回执"。**判定依据**：`completestep.go:300` 用 `HasSuccessfulCommand(command)` 作为验证的兜底凭据。
2. **`DetailedExecutor` 是"两方法"接口**：只实现 `ExecuteDetailed` 而漏掉 `ExecutionDescriptor` 时，类型断言失败，执行元数据**静默**为 nil（不报错）。我第一版 `bash_output`/`wait` 正是如此，靠 `internal/boot` 的真实装配 effect test 才暴露（`go vet`/单测都发现不了）。已补两个方法，并留下注释说明为何两个都要。

### 9.5 档位选择判据（2026-10-10 实测）

`shell_async` 的收益只来自"把**本回合不需要**的等待挪出关键路径"，代价是**被抬走的批内后续调用必须先收作业、再重发**——**除非该命令被宿主证明不改工作区**（`shellsafe.ClassifyBash` 的 `AnyMutation()==false`，例如 `go vet`）：此时后续调用直接照跑，连那一轮也省掉；分类器"未知即按会改"（fail closed），所以 `sleep`/`go test`/`make test` 这类仍走保守的一刀切 defer。所以它换的是墙钟，不是轮数。

| 回合形状（同一批次 = `bash "sleep 2"` + 一次独立 `read_file`） | `off` | `fast` | 账 |
|---|---|---|---|
| 本轮**不需要**慢命令的输出（模型有别的活可做） | 2194 ms / 2 轮 | **54 ms / 3 轮** | 墙钟 −97.5%，付 1 轮 ⇒ **净赚** |
| 本轮**就需要**该输出（下一步拿它做判断） | 2171 ms / 3 轮 | 2230 ms / 4 轮 | 无墙钟收益、多 1 轮 ⇒ **净亏** |

仪器：`internal/boot/loop_async_ledger_effect_test.go::TestEffectOffPathLedgerForALiftedCall`——同一条 provider 脚本在两种档位下各跑一遍，且 provider 只有从工具结果里读到"被延后"才重发，因此它不预知档位，账本由宿主行为决定。

同一账本换成**宿主识别的慢检查**（fixture 里 `Makefile` 的 `test:` 目标睡 2 秒，命令 `make test`；仪器 `…::TestEffectOffPathLedgerForARecognizedCheck`）：

| 回合形状（同一批次 = `bash "make test"` + 一次独立 `read_file`） | `off` | `balanced` | `fast` |
|---|---|---|---|
| 本轮**不需要**检查结果 | 2270 ms / 2 轮 | **47 ms / 3 轮** | 44 ms / 3 轮 |
| 本轮**就需要**检查结果 | 2203 ms / 3 轮 | 2221 ms / 4 轮 | 2236 ms / 4 轮 |

读数：`balanced` 与 `fast` 在**同一条命令**上**同账**（轮数相同、墙钟同量级）——`balanced` 的"保守"只体现在它**挑命令**，不体现在账本上；而"检查的结果常被立刻需要，所以抬它更安全"这个前提**未被数据支持**（需要结果的回合照样净亏 1 轮）。

**启用建议**：按**回合形状**选，别按命令种类选——慢命令与后续工作互不依赖时开 `fast`（或 `balanced`，二者在你命令行形状上等价）；若下一步就是等它的结果，开不开一样、开了反而多花一轮，这种回合保持 `off`。

### 9.7 批处理提示：压缩回合数（P1，2026-10-10）

轮数是墙钟的乘数（本会话实测 10–11 轮/回合、每轮底价 2.4–3.8 s），而现场观察到的调用密度只有约 1.4 个/批。于是宿主在**连续 3 个"单调用只读且成功有据"的回合**之后，往**回合尾部**注入一句批处理提示（`internal/agent/batch_nudge.go`；`Host batching hint`）：

- **只在尾部**：走 `applyInterventions` 的 guidance 通道（与 soft budget / 风暴熔断同一出口），**不碰缓存前缀**；同时它**只提示、不阻止**（`verdictAdvise`），也不改写任何调用参数。
- **重置条件**（"不要带出新问题"的落地）：写者、失败、阻塞、已经批过一轮（多调用）、以及**本轮没有成功回执**（零收益回合属于进度守卫的地盘，让一个卡住的模型批更多调用只会放大浪费）。每回合**至多一次**。
- **实测（脚本模型，合规 vs 忽略同一任务）**：读 8 个文件、一读一轮 ⇒ **9 轮 vs 5 轮**（省 4 个往返）；脚本模型是上界，真实模型是否照做**未验证**。
- **仪器**：`internal/boot/batch_nudge_effect_test.go::TestEffectBatchingHintShortensTheTurnWithoutMovingThePrefix` —— 同一条脚本跑两遍（忽略/照做），并断言**跨轮 system 消息与工具 schema 逐字段不变**、且提示不出现在前缀里；单元层 `internal/agent/batch_nudge_test.go` 钉住阈值、每回合一次与五种重置条件。

**第二条（P2，同日）：扇出提示**。同一个通道、同一个文件里还有一句更晚的提示（`Host fan-out hint`）：一条**只读回合**如果已经批过调用（或批处理提示已经说过）却仍然很长，宿主就把 `parallel_tasks` 摆出来——分支并发时墙钟是**最慢分支**而不是轮数之和；文案同时写明"互相依赖的调用留在本条消息里""小活优先批处理""扇出每个分支各有上下文、要花钱"。两条提示各自**每回合至多一次**，且顺序由代码保证：**便宜的批处理先，贵的扇出后**。

- **阈值两个入口（2026-10-10 收紧）**：①**回合 ≥ 8**（`fanoutNudgeMinRounds`）——已批过调用却还很长的回合；②**廉价修法被无视**——批处理提示说过之后，再连续 `fanoutIgnoredFixRounds`(=3) 个单调用只读回合（`streak ≥ batchNudgeStreak + fanoutIgnoredFixRounds` = 6）就升级到扇出建议。理由是本机实测：**中位回合只有 4 轮、p90 是 12 轮**，把建议压在第 8 轮等于"回合快结束了才说"，而扇出只有能改变剩下一半的回合形状才有意义。谓词收进 `fanoutWorthOffering(rounds)`（原先的 `batchingAddressed()` 折进它，少一个方法）。
- **回头看（这一步修掉的实现 bug）**：最初我把扇出只挂在"轮数 ≥ 8"上，结果一条**从没批过**的长回合会在**第 1 轮**就被劝去扇出——比"先批量"更贵、更绕远。修法是要求"便宜修法已说或已用"成立才允许扇出。**这是单元测试当场抓到的**：`TestFanoutNudgeWaitsForTheCheaperFix` 第一版就红了。
- **仪器**：`internal/agent/fanout_nudge_test.go`（顺序、两种"已具备便宜修法"的路径、短回合不劝、**廉修被无视后升级**与**升级前保持沉默**、写者/失败回合不劝、每回合一次）。**不新增** boot 级夹具：扇出与批处理走的是**同一条** guidance 通道，该通道的边界证明已在 `TestEffectBatchingHintShortensTheTurnWithoutMovingThePrefix` 里（同轮 system/工具 schema 不变）。

### 9.9 压缩口径：什么时候自动维护（只读体检，2026-10-10）

起因是一个**被自己证伪**的假设：我曾怀疑 `context_window = 1000000` 高于 `deepseek-v4-flash` 的真实窗口，"压缩永不触发"于是变成"溢出前不维护"的隐患。查完代码后结论相反，且比假设更细：

| 项 | 事实 | 出处 |
|---|---|---|
| 模型 catalog 窗口 | `deepseek-v4-flash`: Context = **1_000_000**、MaxOutput = 384_000 | `internal/provider/opencode_go.go:37-38` |
| 有效窗口 | `min(配置, 运行时学到的窗口)`——学到值存在时会**夹紧**配置值 | `internal/agent/output_budget.go:363-380` |
| 自动压缩触发 | `max(1, 有效窗口 × CompactRatio)` = `0.8 × 1e6` = **800_000 token** | `internal/agent/compact.go:97-110` |
| 物理输入上限 | `有效窗口 − protocolReserveTokens(256)` | `internal/agent/compact.go:112-120`、`:32` |
| 压缩后保留的逐字尾巴 | 窗口的 **16%** | `internal/agent/compact.go:122-128` |
| 更早的"软"维护 | **没有**：`SoftCompactRatio` / `ToolResultSnipRatio` / `CompactForceRatio` 都是废弃兼容输入，"automatic maintenance is controlled only by CompactRatio" | `internal/agent/agent.go:931-939` |

**结论**：用户的 `context_window` 与 catalog **一致**（不是配大了）；压缩**会**在约 **80 万 token** 触发，而且**溢出有独立的硬上限兜底**（不是只靠 provider 拒绝）。⇒ "长会话越来越慢"是**预期行为**（本会话实测单回合 prompt 63.7k → 80.7k），要更早介入只能靠**配置**：把 `context_window` 设成你愿承担的工作区间（例如 200k ⇒ 压缩在 160k 介入），`compact_ratio` 调低同理。**不需要改代码**。

**已知未知**（无证据表明可达，故未加机制）：一批并行调用的输出总量没有上界（单次输出有 head+tail 截断），理论上可从"<80 万"一步跨过硬上限；是否真实可达需要一份长会话的 `usedTokens` 序列。

### 9.10 上下文经济（P3）的量数据与"不做"结论（2026-10-10）

P3 的代码半边原本要做的第一件事是"工具结果**入账时蒸馏**"。先量后改，量完不做了。

**量数据**（本会话自己的 provider 可见 transcript，`.events.jsonl` 去重后按 role 统计字节）：

| role | 字节 | 占比 | 条数 |
|---|---|---|---|
| tool | 718,222 | **77.2%** | 634（均值 ≈ 1.1 KB） |
| assistant | 99,089 | 10.7% | 511 |
| user | 84,026 | 9.0% | 38 |
| system | 28,748 | 3.1% | 1 |

尾部很薄：**最大 10 条工具结果只占工具字节的 15.9%**，**超过 8 KB 的仅 6 条**（合计 83 KB）。

**读数**：体积确实压在工具结果上，但痛在**条数**而不是**单条体量**。逐条蒸馏 600 条、均值 1 KB 的结果，等于"每 1 KB 花一次模型往返"——按本会话实测的 2.4–3.8 s/轮，这是**速度倒退**，与"提速"目标相反。而单条体量问题**已经**由既有机制处理：

| 已有机制 | 位置 |
|---|---|
| 重复结果摘要 + 截断 | `internal/agent/duplicate_result.go` |
| 重复读只给"原文引用"（`readReference`，不再重发内容） | `internal/agent/read_delivery.go` + `read_delivery_test.go` |
| 工具输出 head+tail 截断（`maxToolOutputBytes`） | `internal/agent/agent_tool_output.go` |
| 重复读评分与升级（novelty guard） | `internal/agent/read_novelty_guard_test.go` |
| 唯一的整体缩减手段：压缩（80 万触发） | §9.9 |

**结论（本节的"不做"）**：P3 的代码半边**没有便宜的剩余收益**——条数问题正是 P1/P2（批处理提示、扇出提示，已落地）在打的靶子；体量问题已被上表机制覆盖；更早的整体缩减只有**配置**（§9.9 的 `context_window` / `compact_ratio`）。**不加模型蒸馏**。

**口径告诫**：字节 ≠ token，且这是**我自己的重工具会话**（30 余回合、634 次调用），所以它说明的是**形状**（工具结果占大头、尾部薄、条数主导），不是普适常数；换到以写代码/长推理为主的会话，比例会不同。
