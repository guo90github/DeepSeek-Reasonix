## 一、现状测量（本轮，真机装配）

仪器：`internal/boot/loop_async_effect_test.go::TestEffectLongForegroundCallHoldsTheLoop`

批次 = `[bash: sleep 2, read_file: note.txt]`，在真实 `Build` 装配上跑一轮：

| 量 | 实测 |
|---|---|
| 该批次结束后、**下一次模型往返**的间隔 | **2137 ms**（≈ `sleep 2` 的全部时长） |
| 同批的后续调用（`read_file`） | 在同一批内**等慢调用结束后才执行** |

## 三、目标语义与口径

1. **不阻塞**：一次循环里遇到会长时间运行的调用，宿主**不因它把整批/整轮拖住**——把该调用转成后台作业，批次立即收口。
2. **事后收取**：作业结果用既有 `bash_output` / `wait_job` 取回；完成时按既有作业通知路径告知。
3. **保序**（不可省的约束）：同批**后续调用不得提前执行**——否则"先写后台跑、后调用来读"会产生顺序错乱的观测。故后续调用要**延迟**（如实说明原因），由模型在收取作业后重发。
4. **单步 ≤1000ms 口径（假设 A-04）**：只计**宿主侧**——即"派发该调用 → 本轮收口"的时间，不含命令自身运行时长、不含模型推理与网络。仪器就是 §一 那支 effect test：把规则打开后，同样的批次里"下一次模型往返"的间隔必须远小于 `sleep 2`（目标 < 1000ms）。

## 四、设计（定稿，实作待做）

**决定必须发生在启动之前。** 前台 `bash` 一旦跑起来就无法热转后台：杀掉重启会重复副作用（写文件、装包、改仓库状态）。因此规则是"启动前判断"，而不是"跑到一半再搬走"。

规则（`executeBatch` 串行路径，`internal/agent/execute_batch.go:266-317`）：

1. 若当前调用是 `bash`，且该参数**未**显式带 `run_in_background`，且**本批在它之后还有未填的调用**，且**档位**判定为"该转"：
   → 就地把该调用参数补上 `run_in_background: true` 后再执行（`bash` 自身会启动作业并立刻返回 `Started background job …`，结果自解释）；
2. 同时把本批其余未执行的调用按"**延迟**"处理：给一条如实的结果——"前序调用已转后台作业 `<job id>`；先用 `bash_output` / `wait_job` 取回它，再重发本调用"（与既有依赖屏障的跳过文案同族，但原因不同，故用独立措辞）；
3. 交付策略（档位）：
   - **极速模式**：只要 `bash` 与本批后续调用同批，就转后台（最激进）；
   - **平衡（默认）**：只对宿主识别为"验证/构建"形状的命令（复用 `evidence.IsVerificationCommand`）转后台，其余保持前台；
   - **关**：一律不自动转（= 今天的行为）。
4. 与既有机制的关系：转后台**不是失败**，不触发依赖屏障；`complete_step` 的回执要求不变（验证类命令被转后台后，必须**先收取**再算数——这是模型侧的行为约束，写进提示词/结果文案）。

**档位与"拖拽按钮"**：档位就是上述**激进度**这一个旋钮；前端拖拽控件是它的界面形态（后续需求第十/第十七同属桌面交互批次）。宿主侧先落"旋钮 + 规则"，界面后接。

### 7.2 ⚠️ R-9 的真身：**收取后台作业不会为原命令留下验证回执**

写文案时查证发现的**功能缺口**（不是文案问题）：

- 前台验证 → `ReceiptFromToolCall("bash", args)` 记下命令文本 → `HasSuccessfulCommand(cmd)` 可匹配 ⇒ `complete_step` 通过；
- 后台作业（自动转或模型显式）→ 回执的 `command` 是**空的**（`bgjobs.go` 全文没有 command 映射，`wait_job`/`bash_output` 也不携带作业的原命令）⇒ 即便模型老老实实收取并拿到退出码 0，**也换不来一条该命令的验证回执**，`complete_step` 仍会认为"这条验证没跑过"。

因此当前文案只能解释现象，**不能真正闭环**。闭环的设计（下一轮实作）：

1. 转后台时（`promoteShellCallToBackground`）与显式后台时，都记下 `jobID → 原命令文本`（promotion 处有 `calls[i].Arguments`；job ID 从该调用的结果/执行元数据取，必要时给 `ShellExecution` 加一个显式 `JobID` 字段，避免解析文案）；
2. 模型收取（`bash_output`/`wait_job`）且作业终态为**成功**时，宿主按记下的原命令补一条 `Receipt`（`ToolName:"bash"`、`Command:原命令`、`Verification` 同前台），退出码取自作业的终态；
3. 补测：`后台跑 go test → 收取 → complete_step 引用它可通过`，以及"作业失败时不得记为成功验证"。

未见此改动前，**默认档保持 `off` 的理由又多一条**（见 7.3）。

### 7.3 ② 三档真机实测与默认档决策

同一支 effect test 家族（`internal/boot/loop_async_effect_test.go`），批次 `[bash(<命令>), read_file]`，机器与装配一致：

| 档位 | 命令 | 本轮实测"下一次模型往返"间隔 | 是否提升为作业 | 后续调用 |
|---|---|---|---|---|
| `off`（默认） | `sleep 2` | ~2138 ms（见第 5 轮基线 2137） | 否 | 正常执行 |
| `balanced` | `go vet ./...`（检查形状） | **11 ms** | 是 | 被延迟 |
| `balanced` | `sleep 2`（普通形状） | **2138 ms** | 否 | 正常执行 |
| `fast` | `sleep 2` | **18 ms** | 是 | 被延迟 |

读数与决定：

1. **`balanced` 并不解决需求里的那个场景**——需求举的例子是"一个 bash 脚本卡几分钟"，脚本属**普通形状**，balanced 依旧等满（2138 ms）。
2. **`fast` 也不宜做默认**：它按"同批有后续调用"一律提升，于是日常的 `[gofmt -w ., go test]` 这类**短命令成链**会被拆成"前者后台、后者延迟"，比今天的串行更糟（多一次收取与重发）。
3. 需求本身要的是**用户可控的档位**（"附带一个拖拽按钮……最高档为极速模式"）⇒ **默认档保持 `off`**，把三档连同上面这张实测表交给用户去选：要检查类提速选 balanced，要在长流程里继续干活选 fast。

> 这也与项目既有的"开关是唯一闸门、且默认不变行为"的口径一致。

## 八、A-23 闭环落地（2026-10-01 第 8 轮）

### 8.1 现在的语义链

| 环节 | 行为 |
|---|---|
| 起动后台 | `bash` 的执行元数据带出 `JobID`（`tool.ShellExecution.JobID`，由 bash 后台分支写入）；宿主记下 `jobID → 原命令`（`shellJobCommands`，`internal/agent/shell_job_receipts.go`） |
| 起动**不算数**（新发现，见 8.2） | 起动那张回执被降级：`Success=false` 且**抹掉 `Command`**（`degradeBackgroundStartReceipt`）——既不再匹配"成功跑过"，也不再匹配"跑过但失败" |
| 收取 | `bash_output` / `wait` 现在**结构化**带出作业终态（`ExecuteDetailed` + `ExecutionDescriptor`），agent 在 `finalize` 里按 `jobID` 取回原命令 |
| 记功 | 终态 **completed** ⇒ 补一条 `bash` 回执（`Command=原命令`、`Success=true`），并在收取结果里写明"collected as receipt r_… for `<cmd>`；cite it to sign this off"；**failed / killed / 仍在跑** ⇒ 不产生成功回执（failed/killed 记一条失败回执，仍在跑什么都不记） |

### 8.2 顺带查出的两个真缺陷（都不是本次新引入，但都影响第九的可用性）

1. **起动一张回执就能冒充"跑过"**：此前 `bash(run_in_background)` 的回执是 `Success=true` + `Command=原命令`，于是 `HasSuccessfulCommand(cmd)` 在**作业还没跑完**时就为真——`complete_step` 会接受一条根本没结束的验证。这条洞在今天之前一直存在（只是以前没人把验证类命令放后台）。修法即 8.1 的"降级起动回执"。**判定依据**：`completestep.go:300` 用 `HasSuccessfulCommand(command)` 作为验证的兜底凭据。
2. **`DetailedExecutor` 是"两方法"接口**：只实现 `ExecuteDetailed` 而漏掉 `ExecutionDescriptor` 时，类型断言失败，执行元数据**静默**为 nil（不报错）。我第一版 `bash_output`/`wait` 正是如此，靠 `internal/boot` 的真实装配 effect test 才暴露（`go vet`/单测都发现不了）。已补两个方法，并留下注释说明为何两个都要。
