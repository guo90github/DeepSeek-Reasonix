# 40 · 第十七「待办管理混乱」调研、复现与队列模型设计

> 阶段：第五阶段之后的修复批次 · 类型：调研 + 设计（本轮完成复现与模型定稿；实作见 §5）
> 需求原话：桌面待办管理混乱修复——**完成的会再次跳出**、**已出的待办有时不展示**、**最新待办顶掉历史未完成待办后历史不可见**；需引入**队列机制**。

## 一、三类现象各自的机制（全部有源码与复现测试支撑）

### S1「完成的会再次跳出」

- 前端把「一批待办」的身份**由当前列表内容算出来**：`todoBatchKey(todos)` = `JSON.stringify(items.map({content, level}))`（`desktop/frontend/src/lib/todoVisibility.ts:151-157`）。
- 用户关掉一批（`dismissTodos` → 宿主 `DismissTodoBatchForTab(tabID, batchKey)`，按 **batchKey** 持久化到会话 sidecar：`desktop/todo_dismissal.go:14-31`）。
- 只要之后模型**增删改任一条目**（加一步、改个措辞），`todoBatchKey` 就变 ⇒ 旧 key 的关闭记录不再命中 ⇒ **同一份清单以"新批次"身份重新出现**：`shouldShowTodoPanel` 回 true（`todoVisibility.ts:166-182`）。
- 唯一稳定的是**状态翻转**（`todoBatchKey` 不看 status）——这正是"完成了会再跳出"的观感来源：完成过程本身不改 key，但任何编辑都改。

复现：`desktop/frontend/src/__tests__/todo-queue-repro.test.ts`（8 条，1 条记录"加了新步骤 ⇒ 关闭过的批次重新出现"，1 条记录"改个措辞也重启"，1 条记录"仅状态翻转才保持身份"）。

### S2「已出的待办有时不展示」

- 面板的数据来源**只有活着的控制器**：`MetaForTab` 填 `CanonicalTodos: ctrlTodos(snap.ctrl)`（`desktop/app.go:6693`），而 `ctrlTodos` 在控制器未绑定时返回 **nil**（`desktop/app.go:6703-6710`，注释明写 "or nil if the controller is not yet bound"）。
- 于是**从历史恢复/刚打开的标签**：transcript 里明明有一份待办清单，前端拿到的却是空 ⇒ `shouldShowTodoPanel(undefined, …)` 直接 false（`todoVisibility.ts:173`）。
- 换言之：清单**已出**（在会话里），但**没有从历史回填的读法**，只能等控制器绑定。

复现：同一文件最后两条（"来源为空 ⇒ 什么都不显示"；"同一份清单只要来自已绑定控制器就正常显示"）。

### S3「最新待办顶掉历史未完成待办后历史不可见」

- 内核只保留**一份最新清单**：`setTodoState` 直接 `a.sess.todoState = NormalizeSerialTodos(todos)`（`internal/agent/agent.go:1431-1434`），每次 `todo_write` 覆盖。
- **没有队列、没有归档** ⇒ 新清单没提到的未完成项**无从查询**（不是被隐藏，是根本不在状态里）。

复现：`internal/agent/todo_state_repro_test.go`
- `TestTodoWriteReplacesThePreviousListWithoutArchive`：先 3 条（含 1 条 in_progress、1 条 pending），再写入 1 条新清单 ⇒ 旧的那两条**不可达**（测试日志明写 "the previous list's unfinished items are unreachable after a replacement"）；
- `TestTodoStateKeepsOnlyTheNewestStatuses`：同一批条目只更新状态时的正确行为（这条是要保住的）。

## 二、根因归纳（一句话）

**"一批待办"在今天既没有稳定身份（S1），也没有第二个数据来源（S2），更没有历史（S3）**——三者都源于同一处：模型只保存"最新的一份清单"，而批次身份、可见性判定、关闭记录全都从这一份快照派生。

## 三、队列模型（A-08 具体化）

```ts
// 内核侧（权威）：队列 + 归档
type TodoEntry = {
  id: string;          // 宿主签发的稳定 id（首次出现时分配；随后随条目沿用）
  content: string;
  status: "pending" | "in_progress" | "completed" | "dropped";
  level: number;       // 0 阶段 / 1 子步
  batchId: string;     // 归属批次（同一批 todo_write 的内容共享）
};
type TodoBoard = {
  queue: TodoEntry[];   // 未完成：按批次先后 + 批内顺序（历史未完成项在此"续排"）
  archive: TodoEntry[]; // 已完成/被丢弃：只读归档，用于"历史可见"
  batches: TodoBatch[]; // 批次元数据：id / 首次时间 / 关闭记录（dismiss 的锚点）
};
```

三条纪律：

1. **身份与内容解耦**：批次身份 = `batchId`（宿主签发、首次出现时分配），不再由内容哈希决定 ⇒ 编辑列表不再让关闭过的批次复活（修 S1）。
2. **可见性 = 队列 + 归档**：面板显示「未完成队列」（无论来自哪一批，**历史未完成项继续在列**）+ 可展开的「已完成归档」；不再用"最新一份清单"当唯一真相（修 S3）。
3. **历史回填**：控制器未绑定时，从会话历史里读最后一次 `todo_write` 的结果**作为只读初始值**（既有能力：`desktop/history_slice.go:1138 historyTodoArgsForSource` / `app.go:6002 historyTodoArgsWithCompleteSteps`）⇒ 恢复的标签也能显示（修 S2）。

迁移：旧数据只有"最新清单"，首次读取时整体成为**一个批次**（`batchId` 由首次出现时间派生），并把它标为 `legacy`——不伪造历史，只保证此后不再丢。

## 五、实作顺序与验收

1. **S1 先修（最小、独立）**：宿主签发 `batchId`（首次出现时分配并持久化）→ 前端身份改用它。验收：加/改/删条目后，关闭过的完成批次**不再复活**；改动前的那 3 条复现断言翻面。
