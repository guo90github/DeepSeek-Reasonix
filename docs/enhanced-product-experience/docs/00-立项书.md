## 一、目标解读与需求清单确认

九条需求分属三条主线：**记忆-上下文体系**、**执行链路稳定化**、**桌面交互与展示**。

| 编号 | 需求 | 意图 | 受益者 |
|---|---|---|---|
| 第七 | `remember` / `memory` 搭配协作改造 | 让记忆真正被用上，同时把常驻上下文的占用压到极小（分层：一层摘要进上下文，二层按需查取） | 用户（省 token）+ 模型（拿得到细节） |
| 第八 | 前置 / 后置强化处理 | 前置=发送前塞入更多有用信息；后置=回传后做一次加工（用途自定） | 模型效果 |
| 第九 | 单次循环内异步不阻塞 + 速度档位控制 | 阻塞点不占住循环，事后回收结果；单步 ≤1000ms；最高档「极速模式」 | 用户（等待时间） |
| 第十 | 桌面端多开 | 标签页脱离主视图，可在窗口任意位置停留、缩放、拖拽 | 用户（多任务并行） |
| 第十一 | 双主线信息流 | 一条给人看、一条给模型读，明确分离、各自优化 | 模型（信噪比）+ 用户（可读性） |
| 第十二 | 工具调用频繁报错的根治 | 从机制上消除，而不是提示模型「注意点」 | 稳定性基线 |
| 第十四 | 会话回顾前端深度定制 | 至少一个热力图或同等丰富渲染 | 用户（可读性） |
| 第十六 | 记忆「召回记录」深度定制 | 与技能、提示词加载协作；前端并入现有面板 | 用户（可控性/信任） |
| 第十七 | 桌面待办管理混乱修复 | 完成的会再跳出、待办有时不显示、新待办顶掉历史不可见 → 引入队列机制 | 用户（可靠性） |

## 二、类型判定与阶段规划

| 阶段 | 类型 | 覆盖需求 | 完成标志 |
|---|---|---|---|
| 第一阶段 · 基线与根因 | 调研 | 第十二、第九（证据面） | 根因图谱落盘：每个拦截码→产生点（file:line）→机制→消除手段；并给出可复算的降幅判据 |

| 第三阶段 · 执行链路稳定化 | 开发 | 第十二、第九 | 报错率与轮次往返下降有测试证明；异步不阻塞有真跑证明（单步 ≤1000ms）；档位控件的「极速模式」可用 |
| 第四阶段 · 记忆与召回落地 | 开发 | 第七、第十六、第十一 | 分层记忆生效（上下文占用可测）；召回记录并入记忆面板；双主线在传输层可分辨 |

顺序理由：稳定性基线（第九、第十二）先行（全局决策规则规定其优先级高于功能需求）；第七/第十一/第十六 先统一设计再分别实现；第十、第十七 互不依赖可并行但排在稳定性之后。

## 三、需求依赖分析

```
第七 ─┐
      ├─→ 记忆-上下文体系（同一份数据、同一份预算、同一套前端面板）
第十一 ┤   · 第七 决定「进上下文的是什么」
      │   · 第十一 决定「这份东西在传输层怎么分流」
第十六 ┘   · 第十六 决定「召回过程怎么被看见与调整」——它消费第七的分层产物
第九 ─┬─→ 执行链路（同一个循环）
第十二 ┘   · 第十二 先消除「无效往返」（读证据门、批量屏障）
           · 第九 再把「真阻塞」挪出循环——顺序不可颠倒，否则异步化会把无效往返一起搬进后台
第十四 ──→ 依赖第十六（回顾/召回都要并入既有面板体系，复用同一渲染与跳转约定）
第十 ─┬─→ 桌面交互（同一个窗口与布局模型）
第十七 ┘   · 第十 改窗口/停靠模型 → 待办面板的挂载点随之改变，故 第十 在前
```

**冲突点**：第十（自由停靠）与第一阶段的「缓存优先」约定（系统提示前缀须字节稳定）无直接冲突；但第十一（双主线）若改动 provider 可见消息，会动到缓存前缀，须以「回合尾部追加」方式实现，不得改前缀（假设 A-05）。
