# 50-第七 / 第十一 / 第十六 统一设计：记忆与信息流

> 需求：第七（remember/memory 分层协作）、第十一（双主线信息流）、第十六（召回记录 + 技能/提示词协作）。
> 三者共用同一条"信息进模型"的通道，**必须先统一再落地**：第七决定"什么该被记住、以什么权限"，第十六决定"记住/用过的痕迹怎么留、怎么查"，第十一决定"这些痕迹与协作事件走在哪条线上、能不能碰到模型"。三者分开实作必然互相打架（典型：第七把新状态塞进系统提示 → 撞缓存纪律；第十六把召回文本塞进事件 → 撞内容无关纪律）。
> 本文件只写**现状事实（源码为据）/ 方案 / 状态模型与纪律 / 验收判据**，不写代码。

## 二、方案

### 2.1 第七：分层协作（读/写权限 + 召回优先级 + 写入门槛）

**A-32（判断题的默认答案，实现时按此执行）：type × scope 的默认矩阵**

| type | 默认 scope | 默认 activation | 理由（用户 2026-08 的两条口径） |
|---|---|---|---|
| `user` | `global` | `pinned`（受 1500 预算约束） | "用户是谁/偏好"跨项目成立，且必须每轮都在 |
| `feedback` | `global` | `pinned`（同上） | 工作方式指导要一直生效；放不下说明它该升级成 `AGENTS.md` 指令 |
| `project` | `project` | `relevant` | 项目内事实，按需召回即可 |
| `reference` | `project` | `relevant` | 外部指针，按需 |
| （框架知识，见下） | `project` | `relevant` | 依用户口径：**"tech stack" 是框架知识介绍，不是依赖分析** |

- **"框架知识"归类**：本设计把用户口中的"framework 知识"落在 `type=project` + 内容标记，而不是新开一个 `type`（A-33）。理由：`type` 已是封闭值域（`store.go:46` 的 `validTypes`），新增会牵动索引渲染、召回、落盘校验四处；而"框架知识介绍"与"项目进行中的约束"在权限上完全同档（project 级、按需召回）。
- **读权限**：所有 type 都可读（`recall` 无过滤）；**pin 只允许 global 的 user/feedback**（沿用 `ResolveActivation` 现状，不放松）。
- **写权限**：
  - 模型自动写（`remember` 工具）→ 只允许 `project` 域；`global` 写必须过一次人工确认（沿用 `claimAutoRemember` 白名单 + `AssessRememberWrite` 的 `Scope` 建议，`remember_policy.go:60` 已在做"非 project 就走另一分支"）。
  - 命中敏感事实（`rememberRequestSensitive`）→ 一律不自动写，转为"建议 + 需确认"。
  - 与既有条目重叠（`rememberRequestOverlaps`）→ 走**更新**而非新增（避免同名重复条目堆积）。
- **召回优先级（定成一条可测的排序）**：
  1. `pinned` 正文（稳定块，恒定在场，不受召回影响）；
  2. `recall` 命中：同分时 **project 优先于 global**（离当前工作更近）、**revision 更新者优先**、`freshness` 未过期的优先（`internal/memory/freshness.go:45-72` 已有窗口与 `FreshnessFor`）；
  3. `ShadowHits`（V2 排序）**只记录，不服务**（沿用 `auto_recall.go:57-59` 的口径）；
  4. 预算：仍走 `CharBudget/UsedChars`，被丢弃的数量必须进记录（见 2.2）。
- **技能与提示词的协作规则**：技能目录只进 `SkillsCatalog` 段（名字/描述/运行标签），**不把技能正文塞进前缀**；技能正文只在 `run_skill` 调用时以工具结果进主线（`skill/tools.go` + `index.go:29` 现状），因此技能增长不撞缓存。

### 2.2 第十六：召回记录（记录什么、写在哪、怎么查）

**目标**：能回答"第几轮、因为什么、用了哪条记忆、有没有真的进模型、被谁挤掉"。

- **记录内容（内容无关 + 内容相关分离）**：
  - **内容无关（可进遥测/日志/导出）**：`turnSeq`、`queryDigest`（查询哈希）、每条 `{id, revision, type, scope, freshness, score, injected: bool}`、`usedChars/omitted/suppressed`、`snapshotDigest`（当轮 session-context 的 `Digest`）。
  - **内容相关（只留本地，供回顾页对照）**：命中条目的 `description`（不是正文），以及被注入文本的哈希。**正文永不进记录**（沿用 `sessioncontext.Diagnostics` 的"never exposes memory text"纪律，`session_context.go:54-56`）。
- **写在哪**：
  1. 轨迹：沿用 `event.MemoryRecallAudit`（已有）**补 `turnSeq` 与 `injected`** ⇒ `internal/trajectory/recorder.go:61` 的镜像字段同步新增；
  2. 会话侧车（新，与既有 sidecar 同款形态）：`memory-recall/v1`，每回合一条压缩记录，**用于回顾页/热力图**（第十四）不重解析轨迹；
  3. **绝不进系统提示、绝不进工具面**（硬纪律，见 §3.2 D-6）：记录是"关于记忆的元数据"，模型不需要它，塞进去就是缓存与污染的双重代价。
- **怎么查**：
  - 会话级：`memory-recall` 侧车按 `turnSeq` 排序，给回顾页每个回合加一行"本轮召回 N 条（含被挤掉 M 条）"；
    **同一份记录也挂在既有记忆面板的「召回记录」页**（2026-10-03 补：`MemoryPanel` 的活动页用 `RecallRecordForTab(tabId)`
    驱动同一个 `RecapRecallStrip`——按 tab 取、无需会话路径；这是需求原文"前端展示需加入现有面板模块"的落点）；
  - 全局级（第十四热力图）：按 `id` 聚合"哪条记忆被用了几次、最近一次第几轮、命中后是否被完成/被推翻"；
  - **推翻检测**：记录里带 `revision` ⇒ 后续若该条被 `remember` 更新，热力图能显示"这条结论已被新版本取代"（这是 2026-08 记忆里反复出现的失效模式：旧结论被复述）。
- **与技能/提示词记录的合流**：技能方面只记"本回合是否调用了技能（`run_skill` 的 name + skill 版本哈希）+ 本次 session-context 的技能目录 `Digest`"；**不记录技能正文**。理由与召回一致：目录变化本身就是可解释的信号（"技能被换过 → 行为变了"）。

### 2.3 第十一：双主线信息流

**定义（先钉死语义，再谈 UI）**：

| 线 | 内容 | 落点 | 能不能进系统提示 |
|---|---|---|---|
| **主线** | 本会话的回合流：用户输入、推理、回答、工具派发/结果、usage、本回合内的 notice/phase | 转录（持久）+ 事件通道（流式） | 只有"回合正文"能进（前缀不行） |
| **副线 A：外来引导** | 外部唤醒：HTTP/push/ACP/bot/房间唤醒 | 逐字落进**回合正文**并带 `[remote wake source=… item=…]` 标记（契约已冻结） | 只允许进正文（`COLLAB-SURFACE.md` §2 位置约束） |
| **副线 B：宿主通知** | 与回合无关的提示：截断、阻断、压缩、状态横幅 | 事件通道的 `Notice` / 状态横幅 / 覆盖层；**不写转录正文** | 不进（前缀要字节稳定） |
| **副线 C：只读投影** | 面板/停靠/活动栏看到的东西：任务队列、改动概览、归档、会话列表、运行中标记 | 从状态投影而来（前端本地 + 元数据） | **不进**（面板/档位状态不进系统提示与工具面——既有约定） |

**方案要点**：
1. **每条副线事件必须声明它属于 A/B/C 哪一类**，并在类型层面固定（例如副线事件的构造点必须给出 `delivery` 字段）。理由：现存 bug 模式就是"某条事件本该是 B，却被当 A 塞进回合正文"或反之。
2. **副线 A 的入口收敛**：所有外来文本一律经 `inbox`/wake 一条路（`internal/boot/inbox_wake.go` + `internal/control/inbox_wake_marker.go`），**不允许**任何其它路径直接把外部文本写进回合——这是"位置约束"能守住的前提。
3. **副线 C 的边界**：面板只读状态；面板上的任何状态（档位、折叠、停靠、归档展开）**不得**反向进提示/工具面（第九/第十/第十七各自的设计里已写同一条，这里升级为统一纪律）。
4. **主线的"副线化"**：工具结果里的长输出、协作事件的长文本，走"引用 + 摘要"（转录只放摘要 + 折叠全文），避免主线被副线淹没；这一条直接对应需求第十四（回顾/统计）与第九（异步不阻塞）的既有取舍。
5. **出口**：副线 B/C 一律经 `event` 通道到前端（`docs/COLLAB-SURFACE.md` 的拒绝分类是它对外可见的那一面），**不做**任何"直接改提示"的旁路。

## 三、状态模型与纪律

### 3.1 状态分类（三类，各有生命周期与出口）

| 类别 | 例子 | 生命周期 | 出口（谁能读） | 能否进提示 |
|---|---|---|---|---|
| **会话态** | 召回记录、队列、归档、待办批次、面板折叠/停靠 | 本会话（sidecar 持久） | 控制器 → 元数据/事件 → 前端 | 否 |
| **持久态** | 事实文件、`MEMORY.md`、`REASONIX.md`/`AGENTS.md`、技能文件、输出风格 | 跨会话 | 存储层 → session-context 分段 | **只有** pinned 正文与目录类摘录可进（有预算） |
| **展示态** | 折叠状态、停靠位置、悬浮矩形、滚动位置、档位控件当前值 | 前端本地（localStorage） | 只给前端 | 否 |

### 3.2 硬纪律（D-1…D-8）

- **D-1**：系统提示前缀**字节稳定**；任何新状态都不许直接改前缀，只能"进段（有预算）"或"进回合尾"。
- **D-2**：`pinned` 正文总量受 1500 字符预算；需要长期生效的规则属于 `REASONIX.md`/`AGENTS.md`，不属于记忆。
- **D-3**：面板/档位/停靠/滚动等**展示态**永不进系统提示与工具面。
- **D-4**：副线 A（外来引导）只进回合正文并带冻结标记；副线 B/C 不进正文。
- **D-5**：`ShadowHits`（V2 排序）只做记录，永不服务；记录与服务的分叉必须在类型上可见。
- **D-6**：召回记录**内容无关**部分可外发；正文只在本地，且**记录本身绝不进提示**。

### 10.4 结论与方案

1. **未达标，且瓶颈不在正文而在「第一层」**：改造确实压掉了正文常驻（全部 global `user`/`feedback` → 4 条 pinned），

   所以策略差只剩 2 条 912 字节。占 93.9% 的索引段改造从未触及。
2. **索引行本身违反用户预设**：「第一层摘要不超过 50 字」要求每条 ≤50 字，实测中位 359 字节、最长 1,162 字节（≈34–387 汉字）——
   长标题 + 由标题派生的长 kebab 文件名（链接目标）一起被塞进了每回合常驻的快照。
3. **方案（下一单元，实施后再复测）**：第一层改为「`- [scope/type] ≤50 字摘要`」，**不再带长 kebab 链接**；
   第二层按需取仍走既有 `memory` 工具（`search` / `read` / `list`，模型按摘要关键词查），自动召回本就走
   BM25/CJK 索引（`recall_index.go`），不依赖可见索引行。
   实测重渲染投影：索引 38,900 → **8,807** 字节 ⇒ 常驻 ≈ (439+2,119+8,807) = **11,365** 字节，
   相对改造前 **0.27**、相对当前 **0.27** —— 两条口径同时达标。
4. **边界/风险**：改的是 session-context 快照的段内容（**不是** provider 缓存前缀），守门用例是
   `internal/boot/prompt_stability_test.go::TestBackgroundMemoryAndSkillCatalogChangesDoNotChangeSystemPrompt`；
   受影响的既有断言（`internal/memory` 索引渲染、`internal/control/session_context_test.go`）须一并更新，
   且必须复测**召回质量**（索引变短后模型是否还能选对要读的事实）。
