# Agent 评测体系 — 全览参考

> 来源：美团技术博客《Agent 评测白皮书》系列 01《Agent 评测全览》（2026-09-10，https://mp.weixin.qq.com/s/hBSIPQnsBeWwX9UZLjWYFA）
> 性质：外部方法论蒸馏。本文把该系列的"全览篇"整理成可引用的结构，供 `docs/agents` 下多智能体协作体系的评测设计对齐语言与优先级。
> 系列定位：本系列分四篇（全览 / 冷启动 / 扩量 / 自进化），本文只覆盖第一篇。

## 1. 结论先行

完备的 Agent 评测体系 = **四个模块、三种能力、两条 Loop、一套资产**。

- **四个模块**：离线评测守住已知；在线评测与监控发现未知；Case 挖掘与归因定位和分派；观测基建作为一切的地基。
- **三种能力**：发现问题、定位问题、驱动演进。缺一项，体系就在对应环节卡住。
- **两条 Loop**：Agent 迭代 Loop（能力持续提升）+ 评测体系迭代 Loop（量具持续校准），二者在 Case 挖掘与归因处共享入口、在评测集处共享资产。
- **一套资产**：覆盖各功能模块的端到端与过程评测集（评测标准 + 评测样本）。

全景图是"终局"而非"起点"：起步阶段让数据飞轮转起来，远大于设计精妙体系。

## 2. 为什么评测认知稀缺

搭 Agent 的门槛在快速降低（基座模型能力进化 + 框架功能丰富），但把 Agent 做好的认知仍稀缺。过去三年大多数 Agent 项目死于缺少可靠的判断机制：

| 死法 | 表现 | 共同根因 |
|---|---|---|
| 停在 Demo | 演示好，接真实流量覆盖不住 | 说不清当前版本行不行 |
| 卡在扩量 | 放量后问题集中暴露，不敢改 | 说不清问题出在哪一层 |
| 说不清业务价值 | 换模型、改 Prompt，无证据 | 说不清改完是否真变好 |

评测的核心目的只回答两个问题：**Agent 好不好？到底哪里好、哪里不好？** 前者给判断，后者给方向。

## 3. 两条 Loop

两条 Loop 共享同一批线上真实样本，通过 Case 挖掘与归因这个枢纽咬合：

1. **评测体系迭代 Loop（评测演进）**：线上信号 → Case 池 → 归因。归因结论是"评测集没覆盖"就补样本；是"评测标准判错了"就迭代 Metrics 与 Rubric。让评测集逐步逼近真实反馈，消除独裁者偏差。
2. **Agent 迭代 Loop（Agent 演进）**：同一批样本归因到 Agent 本身（Prompt 不明确、Skill 描述误导路由、上下文丢信息、模型能力不够）→ 变更 → 评测集回测 → 上线 AB 观察。

第二个咬合点是评测资产：评测集越完善，回测门禁价值越高；门禁越严格，上线暴露的新问题越少，形成正反馈。

## 4. 四个模块

### 4.1 离线评测：变更的门控

依赖三个"固定"：固定评测集（样本 + 标准）、尽可能贴近生产的固定执行环境。回测本质是控制变量对比——只让 Agent 版本变化，分数差异才能归因到版本变更。

**评测集 = (问题、参考答案、评价标准) 三元组**，其中问题-参考答案合称评测样本。借用 Anthropic 的定义，每行三元组是一个 **Task**：固定输入 + 明确成功标准。评价部分由 **Metrics 和 Rubric** 构成，Rubric 是最小粒度评测标准。

Agent 形态从 ChatBot 演进到长程 Agent 后，评测从"答案评测"走向"行为评测"：参考答案变成对执行过程的描述，看的是**路径是否符合预期 + 最终环境状态是否达成目标**。

**评测集分类**：

- **端到端评测集**：看最终结果，回答"事有没有办成"。按用户视角的功能模块分别建立。
- **过程评测集**：看执行过程，回答"中间哪一步出了问题"。可继续分层拆解（知识库评测集 → Skill 评测集 → …），随真实问题驱动细化，不要过早拆太细。

> 经验：端到端回答"要不要拉响警报"，过程回答"警报响了该找谁"。只有端到端会"知道坏了不知道哪坏了"；只有过程会"每个模块都达标但用户不满意"。分层拆解的额外收益是责任清晰——某层分数下降直接找到负责人。

**回测执行的三个工程考量**：

1. **多次试验取稳定结论**：大模型输出有随机性，用 Pass@k 的通过率（Pass Rate）而非单次通过与否。
2. **分层门禁**：安全类、数据准确性类 Rubric 一票否决；体验类、加分项设阈值。
3. **接入研发流程才有约束力**：把回测嵌入 CI/CD 或发布流程。没接入流程的门禁本质上只是建议。

**离线评测的固有局限**：只能发现已知问题——评测集里没有的场景永远测不出来。所以离线负责守住已知，在线负责发现未知。

### 4.2 在线评测与在线监控

- **在线评测**：AB、影子模式、巡检。回答"系统工作得**好不好**"（质量视角）。
- **在线监控**：Skill/Tool 成功率、失败率、Token 消耗、异常波动等运行指标。回答"系统有没有在**正常工作**"（运维视角）。

典型区分：Skill 调用成功率 100% 但每次都返回错误数据——监控是绿的，评测是红的。

三种在线评测手段的互补：**影子模式**在上线前用真实流量兜底，**AB** 在上线后确认业务价值，**巡检**在日常持续盯住基本盘。

**巡检**是两模块的交集，兼具两种属性：

- 评测属性：看某类能力是否持续稳定（质量判断）。
- 监控属性：把分数变化、失败样本、异常趋势沉淀为 Case 挖掘与归因的输入（信号产出）。

**监控三个维度**：

| 维度 | 内容 | 价值 |
|---|---|---|
| 可用性类 | Skill/Tool 调用成功率、失败率、超时率、异常类型分布 | 最基础、最容易见效 |
| 成本类 | Token 消耗、单任务平均步数、平均耗时 | 成本与效率 |
| 行为监控类 | 任务类型分布、Skill 调用频次、平均对话轮次 | 发现用户结构变化 → 提示评测集该扩充 |

稳定性指标与行为指标必须一起看：完成率降 5 个点，若某 Skill 失败率 2%→15% 是工程问题；若 Skill 都正常而"数据对比类"任务占比 10%→35%，是用户结构变了、Agent 在新场景能力不足。两者应对完全不同。

### 4.3 Case 挖掘与归因：驱动双环演进的枢纽

职责分工：**Case 挖掘**把样本收进 Case 池；**归因**继续往下定位，判断 Agent 流程里的核心问题点。这是"Agent 自进化"的核心切入点。

**四大类来源（必须搭配使用，盲区不同）**：

| 来源 | 盲区 |
|---|---|
| 线上反馈 | 只能看到用户愿意抱怨的问题 |
| 监控指标 | 只能看到能被指标刻画的问题 |
| 规则挖掘 | 只能看到自己已经想到的风险 |
| 随机采样 | 唯一能发现"你根本没想到的问题"，成本最高、命中率最低，但不可省略 |

**Case 池分化**：

- **Bad Case → 错题集**：回报最直接。"每一个曾经犯过的错，都不应该再犯第二次"。
- **Good Case → 黄金集**：容易被低估。Bad Case 告诉你哪里不行，黄金集告诉你"到什么程度才算行"，是团队对"好"的可指认共识。

**归因**：一个 Bad Case 只能说明"这里出了问题"，归因回答"为什么出问题"。做法是把 Agent 执行过程全链路铺开，通过 Trace 日志逐一定位问题环节（与查日志 debug 高度雷同），可人工可机辅。

归因后分流（关键判断）：

- 进入 **Agent 效果迭代**：修复 → 回测 → 上线（Agent 迭代 Loop）。
- 校验 **Rubric**：现有 Rubric 没有准确刻画风险 → 迭代 Rubric + Case 流入错题集（评测体系迭代 Loop）。

> 隐蔽陷阱：很多团队默认"评测说不行就是 Agent 不行"，会把 Agent 优化成"迎合评测标准"而非"解决用户问题"。评测标准有偏差时，优化得越努力偏离真实需求越远。定期检查"是不是评测判错了"是体系自我校准的必要动作。

### 4.4 观测基建：一切的地基

"看不见的问题，几乎不可能被稳定解决。"观测的核心价值是让 Agent 链路白盒化——这也是"**观测 + 评测 = 持续迭代**"公式里观测排第一位的原因。

Agent 一次执行是长链路：用户输入 → 意图理解 → 任务规划 → 工具/Skill 调用 → 环境交互 → 中间结果处理 → 策略调整 → 最终输出。任何一层出问题最终效果都可能劣化；若只能看到"用户说了什么"和"最后回复了什么"，几乎无法定位根因。

**务实建设思路**：不必启动之初就建完备系统，按需求反向设计。判断标准——当发现"想自动化判断某件事，但数据里没有"时，就是补埋点的时候。冷启动阶段底线是**最小可归因**：至少拿到完整的模型调用输入输出 + Skill 调用记录，能凭 Trace 复现一个 Bad Case 到底发生了什么。

## 5. 成熟度自查

三种最常见的"部分完备"形态（都有明确缺口）：

1. 只有离线评测：能守住已知，发现不了未知。
2. 只有在线监控：知道系统在跑，不知道做得好不好。
3. **有评测集也有监控看板，但缺 Case 挖掘与归因枢纽**：两套体系割裂，线上问题回不到评测集，评测集结论解释不了线上现象。这种投入不少、收效有限，最值得警惕。

**使用原则**：不要追求所有维度都到 L3。冷启动 = 观测 L1 + 评测集 L1 + 回测门禁 L1 即可最小闭环；扩量重点把评测标准与在线评测推到 L2；全量运营才考虑 L3 自动化与规模化。更有效的用法是看"短板"与"错配"：评测标准已 L3 但 Case 挖掘还是 L0（靠用户投诉），再精密的机评也只是重复评测已知样本——**体系的能力上限由最短的那块板决定**。

## 6. FAQ 要点

- **Agent 离线评测为何不像基座模型那样"必须比上次得分高才发版"？** 基座模型是通用能力（可拆解 benchmark）；Agent 服务垂直业务，最佳指标是业务指标，上线 AB 看业务指标变化才是黄金标准。
- **必过集 vs 挑战集**：必过集是核心功能，已知问题必须尽可能解决才能上线；挑战集构建极难、易跟不上版本迭代。所以离线评测主要用于回测，真实效果靠线上 AB。若设挑战集，必须及时更新以拟合线上真实分布，否则不置信。

## 7. 对 Reasonix 的映射

- **观测**：Reasonix 的 trajectory / event log（JSONL 可重放）已具备"最小可归因"能力，是评测地基的现成实现。
- **离线评测**：`docs/eval/` 与 capability-replay 机制对应"固定环境回测"；需补充的是评测集（Task 三元组）的资产化管理与 Pass@k 门禁。
- **过程评测**：多智能体协作体系（`multi-agent-collaboration-design.md`）的评测应优先建端到端集（协作任务是否收敛交付）+ 关键过程指标（propose/bid/commit 成功率、仲裁次数、收敛轮次），对应"警报响了该找谁"。
- **在线监控**：协作运行时的成本（token/轮次）、静默窗口、消息量上限本就有界，可直接作为监控指标，但还需行为维度（任务类型分布）以发现评测集盲区。
